# B-code-generation: Generating Files with configure_file()

Many projects need to embed build-time information such as version numbers, compiler details, or feature flags directly into their source code. CMake's `configure_file()` command reads a template file, substitutes CMake variables into it, and writes the result to the build directory. This lets you keep version numbers in one place (CMakeLists.txt) and have them automatically appear in your compiled program.

## Concepts

- **configure_file()**: Reads an input file, replaces variable references with their current CMake values, and writes the result to an output file. This happens at configure time (when you run `cmake ..`), not at build time.
- **@ONLY substitution mode**: When `@ONLY` is specified, only variables wrapped in `@VAR@` are replaced. Without it, CMake would also replace `${VAR}` patterns, which can conflict with C/C++ code or shell scripts embedded in templates.
- **Template files (.in convention)**: By convention, template files use the `.in` extension (e.g., `version.h.in`). This signals to developers that the file is a template processed by CMake, not a file to be edited directly.
- **Build directory outputs**: Generated files are placed in the build directory (`${CMAKE_BINARY_DIR}`), keeping the source tree clean. The build directory path is then added to the include search path so the compiler can find the generated headers.
- **project(... VERSION x.y.z)**: Setting a version in the `project()` command automatically defines `PROJECT_VERSION`, `PROJECT_VERSION_MAJOR`, `PROJECT_VERSION_MINOR`, and `PROJECT_VERSION_PATCH` variables.

## File Structure

```
B-code-generation/
├── CMakeLists.txt          # Defines project version, runs configure_file()
├── README.md
├── build.sh
├── build.bat
├── templates/
│   └── version.h.in       # Template with @VAR@ placeholders
└── src/
    └── main.cpp            # Uses the generated version.h
```

After building, the build directory will also contain:
```
build/
└── generated/
    └── version.h           # Generated file with actual values
```

## Code Walkthrough

### templates/version.h.in

```cpp
#ifndef VERSION_H
#define VERSION_H

// Auto-generated by CMake — do not edit manually
#define PROJECT_NAME "@PROJECT_NAME@"
#define PROJECT_VERSION "@PROJECT_VERSION@"
#define PROJECT_VERSION_MAJOR @PROJECT_VERSION_MAJOR@
#define PROJECT_VERSION_MINOR @PROJECT_VERSION_MINOR@
#define PROJECT_VERSION_PATCH @PROJECT_VERSION_PATCH@

#define COMPILER_ID "@CMAKE_CXX_COMPILER_ID@"
#define BUILD_TYPE "@CMAKE_BUILD_TYPE@"

#endif
```

Each `@VARIABLE@` placeholder will be replaced with the corresponding CMake variable value. String values are wrapped in quotes in the template because they need to be valid C string literals. Numeric values (MAJOR, MINOR, PATCH) are left unquoted since they are integer macros.

### CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.16)
project(code_generation VERSION 2.1.3)

configure_file(
    templates/version.h.in
    ${CMAKE_BINARY_DIR}/generated/version.h
    @ONLY
)

add_executable(code_generation src/main.cpp)

target_include_directories(code_generation PRIVATE
    ${CMAKE_BINARY_DIR}/generated
)
```

Key points:
- `project(code_generation VERSION 2.1.3)` sets `PROJECT_VERSION` to `"2.1.3"`, `PROJECT_VERSION_MAJOR` to `2`, `PROJECT_VERSION_MINOR` to `1`, and `PROJECT_VERSION_PATCH` to `3`.
- `configure_file()` takes the input template, performs substitution, and writes to the build directory. The `@ONLY` flag ensures only `@VAR@` patterns are replaced.
- `target_include_directories()` adds the generated directory to the include path so `#include "version.h"` works.

### What gets generated

After running `cmake ..`, the file `build/generated/version.h` will contain:

```cpp
#define PROJECT_NAME "code_generation"
#define PROJECT_VERSION "2.1.3"
#define PROJECT_VERSION_MAJOR 2
#define PROJECT_VERSION_MINOR 1
#define PROJECT_VERSION_PATCH 3
#define COMPILER_ID "GNU"          // or "MSVC", "Clang", etc.
#define BUILD_TYPE ""              // or "Debug", "Release", etc.
```

### src/main.cpp

```cpp
#include <iostream>
#include "version.h"

int main() {
    std::cout << PROJECT_NAME << " v" << PROJECT_VERSION << std::endl;
    std::cout << "Version: " << PROJECT_VERSION_MAJOR << "."
              << PROJECT_VERSION_MINOR << "."
              << PROJECT_VERSION_PATCH << std::endl;
    std::cout << "Compiler: " << COMPILER_ID << std::endl;
    std::cout << "Build type: " << BUILD_TYPE << std::endl;
    return 0;
}
```

The main file includes the generated `version.h` and prints all the embedded build information.

## Building

**Linux / macOS:**
```bash
chmod +x build.sh
./build.sh
```

**Windows:**
```batch
build.bat
```

**Manual build with explicit build type:**
```bash
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build .
```

## Expected Output

```
code_generation v2.1.3
Version: 2.1.3
Compiler: GNU
Build type:
```

The compiler and build type values will vary depending on your system and the options passed to CMake. For example, with `-DCMAKE_BUILD_TYPE=Release`, the build type line would show `Release`.

## Key Takeaways

1. **configure_file()** is the standard way to embed build-time information into source code. It runs at configure time, so the generated file reflects the state of variables when `cmake` was invoked.
2. **Use @ONLY** to avoid accidental substitution of `${...}` patterns in your templates. This is especially important when templates contain shell scripts, C++ code with `${expression}`, or other content that uses dollar-brace syntax.
3. **Generated files go in the build directory**, not the source tree. This keeps version-controlled files clean and avoids accidentally committing generated content.
4. **project(VERSION x.y.z)** automatically creates the `PROJECT_VERSION_MAJOR`, `PROJECT_VERSION_MINOR`, and `PROJECT_VERSION_PATCH` variables. You do not need to set them manually.
5. **Re-running cmake** regenerates the output file. If you change the version in `project()` and re-run `cmake ..`, the generated header updates automatically.

## Exercises

1. Add a `PROJECT_VERSION_TWEAK` component by changing the version to `2.1.3.4` and updating the template to include it.
2. Create a second template that generates a `config.cmake` or `buildinfo.txt` file with human-readable build information (not a C header).
3. Remove the `@ONLY` flag and add a `${CMAKE_SOURCE_DIR}` reference in the template. Observe that both `@VAR@` and `${VAR}` syntax now get substituted.
4. Use `configure_file()` to generate a `.rc` (Windows resource) file or a `.plist` (macOS) file that embeds the version into the binary metadata.
5. Add a custom CMake option (e.g., `option(ENABLE_FEATURE_X "Enable feature X" ON)`) and include it in the generated header as a `#define` or `#undef` based on the option value using `#cmakedefine`.
