# B-version-config: CMake Package Config and Version Files

This example demonstrates how to create a proper CMake package that other projects can consume via `find_package()`. You will learn how to export targets, generate config and version files, use namespace aliases, and leverage `GNUInstallDirs` for portable install paths. This is the standard pattern used by well-maintained C++ libraries.

## Concepts

### The Problem

When project A builds a library and project B wants to use it, project B needs to know: where are the headers? Where is the library file? What compile features does it require? Manually specifying `-I` and `-L` flags is fragile and non-portable.

CMake solves this with **package config files**. After project A installs itself, it leaves behind small `.cmake` files that project B can load via `find_package(MyLib)`, which automatically sets up all include paths, link libraries, and compile requirements.

### The Three Config Files

A complete CMake package installation produces three files:

1. **MyLibTargets.cmake** -- generated by `install(EXPORT ...)`. Contains the imported target definitions (include dirs, link libraries, compile features). This is the mechanical output.

2. **MyLibConfig.cmake** -- generated from your `.cmake.in` template by `configure_package_config_file()`. This is the entry point that `find_package()` loads. It typically just includes the Targets file and runs `check_required_components()`.

3. **MyLibConfigVersion.cmake** -- generated by `write_basic_package_version_file()`. Lets `find_package(MyLib 1.0)` check whether the installed version satisfies the requested version.

### ALIAS Targets

```cmake
add_library(MyLib::mylib ALIAS mylib)
```

This creates a namespaced alias so that the library can be referred to as `MyLib::mylib` both in the build tree and after installation. The `::` in the name causes CMake to treat it as an imported target name, which means a typo like `MyLib::mylibb` produces a clear error instead of silently failing.

### GNUInstallDirs

The `GNUInstallDirs` module provides standard variables for install destinations:

| Variable | Default (Linux) | Default (Windows) |
|----------|-----------------|-------------------|
| `CMAKE_INSTALL_BINDIR` | `bin` | `bin` |
| `CMAKE_INSTALL_LIBDIR` | `lib` or `lib64` | `lib` |
| `CMAKE_INSTALL_INCLUDEDIR` | `include` | `include` |

Using these variables instead of hardcoded paths ensures your package follows platform conventions, especially on Linux where `lib` vs `lib64` varies by distribution.

### EXPORT

```cmake
install(TARGETS mylib EXPORT MyLibTargets ...)
install(EXPORT MyLibTargets
    FILE MyLibTargets.cmake
    NAMESPACE MyLib::
    DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyLib
)
```

The `EXPORT` keyword on `install(TARGETS ...)` records the target for later export. The `install(EXPORT ...)` command then generates the `MyLibTargets.cmake` file containing imported target definitions with the `MyLib::` namespace prefix.

### Version Compatibility Modes

`write_basic_package_version_file()` supports four compatibility modes:

| Mode | Meaning |
|------|---------|
| `AnyNewerVersion` | Any version >= requested version is accepted |
| `SameMajorVersion` | Major version must match, minor/patch can be >= |
| `SameMinorVersion` | Major and minor must match, patch can be >= |
| `ExactVersion` | Exact match required |

`SameMajorVersion` is the most common choice, following semantic versioning conventions.

### @PACKAGE_INIT@

The `configure_package_config_file()` function processes your `.cmake.in` template, replacing `@PACKAGE_INIT@` with helper code that sets up path variables relative to the config file's install location. This makes the package relocatable -- it works regardless of where the install prefix ends up.

## Code Walkthrough

### cmake/MyLibConfig.cmake.in

```cmake
@PACKAGE_INIT@

include("${CMAKE_CURRENT_LIST_DIR}/MyLibTargets.cmake")

check_required_components(MyLib)
```

This is the template for the package config file. When processed by `configure_package_config_file()`:

- `@PACKAGE_INIT@` is replaced with boilerplate that sets up `PACKAGE_PREFIX_DIR` and provides helper macros.
- `${CMAKE_CURRENT_LIST_DIR}` resolves to the directory where the config file is installed, allowing it to find `MyLibTargets.cmake` next to it.
- `check_required_components()` verifies that all components requested in `find_package(MyLib COMPONENTS ...)` are available.

### CMakeLists.txt

**Library with alias:**

```cmake
add_library(mylib src/mylib.cpp)
add_library(MyLib::mylib ALIAS mylib)
```

The alias ensures consistent naming. Consumers always use `MyLib::mylib`, whether they are in the same build tree (via `add_subdirectory`) or finding the installed package (via `find_package`).

**Compile features:**

```cmake
target_compile_features(mylib PUBLIC cxx_std_11)
```

This requirement propagates to consumers -- any project linking to `MyLib::mylib` will automatically have C++11 enabled.

**Export and install targets:**

```cmake
install(TARGETS mylib
    EXPORT MyLibTargets
    LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}
    ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR}
    RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}
)
```

The `EXPORT MyLibTargets` keyword associates this target with the named export set. All three destination types are specified to handle static libraries, shared libraries, and DLLs correctly across platforms.

**Generate and install config files:**

```cmake
configure_package_config_file(
    cmake/MyLibConfig.cmake.in
    ${CMAKE_CURRENT_BINARY_DIR}/MyLibConfig.cmake
    INSTALL_DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyLib
)

write_basic_package_version_file(
    ${CMAKE_CURRENT_BINARY_DIR}/MyLibConfigVersion.cmake
    VERSION ${PROJECT_VERSION}
    COMPATIBILITY SameMajorVersion
)
```

Both files are generated into the build directory, then installed alongside the targets file.

### How a Consumer Uses This Package

After installing MyLib, a consuming project writes:

```cmake
cmake_minimum_required(VERSION 3.16)
project(consumer)

find_package(MyLib 1.0 REQUIRED)

add_executable(app main.cpp)
target_link_libraries(app PRIVATE MyLib::mylib)
```

The consumer runs CMake with:

```bash
cmake -B build -DCMAKE_PREFIX_PATH=/path/to/mylib/install
```

`find_package(MyLib 1.0 REQUIRED)` will:
1. Search for `MyLibConfig.cmake` in standard locations and `CMAKE_PREFIX_PATH`.
2. Load `MyLibConfigVersion.cmake` to verify version 1.2.0 satisfies the 1.0 request (it does, under `SameMajorVersion`).
3. Load `MyLibConfig.cmake`, which includes `MyLibTargets.cmake`.
4. The imported target `MyLib::mylib` becomes available with all its properties.

## Key Takeaways

1. **Three files make a package**: `*Targets.cmake` (generated by export), `*Config.cmake` (your template), and `*ConfigVersion.cmake` (generated by the version helper). All three are needed for a complete `find_package()` experience.

2. **Use ALIAS targets with `::`** so that the library name is consistent between `add_subdirectory()` and `find_package()` usage, and so that typos produce clear errors.

3. **Use GNUInstallDirs** instead of hardcoded `lib`, `bin`, `include` paths. This handles platform differences like `lib64` on some Linux distributions.

4. **EXPORT links install(TARGETS) to install(EXPORT)** -- the `EXPORT` keyword on `install(TARGETS)` is what connects a target to the export set that `install(EXPORT)` writes out.

5. **SameMajorVersion is the standard** compatibility mode for libraries following semantic versioning. It allows consumers to request any version with the same major number.

6. **configure_package_config_file() makes packages relocatable** by using `@PACKAGE_INIT@` to set up paths relative to the config file location, rather than using absolute paths baked in at install time.

7. **Compile features propagate** through exported targets. If your library requires C++11, consumers automatically get that requirement when they link to your target.

## Exercises

1. **Create a consumer project**: Make a new CMake project that uses `find_package(MyLib 1.0 REQUIRED)` and links to `MyLib::mylib`. Build it with `-DCMAKE_PREFIX_PATH` pointing to the install directory from this example.

2. **Test version compatibility**: Change the consumer to request `find_package(MyLib 2.0 REQUIRED)` and observe the error. Then try `find_package(MyLib 1.5 REQUIRED)` -- does it succeed? Why?

3. **Add a second library**: Create a `mylib_extra` library in this project, add it to the same export set, and verify that consumers can use both `MyLib::mylib` and `MyLib::mylib_extra` after `find_package()`.

4. **Switch to ExactVersion compatibility**: Change `SameMajorVersion` to `ExactVersion` in `write_basic_package_version_file()`, reinstall, and test what version strings the consumer can request.

5. **Add components**: Modify the config template to support `find_package(MyLib COMPONENTS extra)` by conditionally including additional target files based on requested components. Use `check_required_components()` to validate.
